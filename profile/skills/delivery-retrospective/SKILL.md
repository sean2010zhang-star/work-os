# 交付后复盘 Skill

## 触发条件
- 完成一个版本交付（patch/minor/major）
- 完成一个复杂任务（三省六部流程结束后）
- 修复了一个重大bug后
- 每日工作结束时

## 核心铁律

> 每段交付物必须经**阶段审查通过**后才能进入下一步。不通过则修改后重新审查。全量完成后全流程测试 + 需求一致性审查。

---

## 流程

### 阶段 Gate 体系（适用于所有复杂任务）

| Gate | 时机 | 审查内容 | 结果 |
|------|------|----------|------|
| **Pre-flight** | 方案设计完成后、编码前 | 方案完整性、设计可行性、风险评估 | 通过 → 编码 / 打回修改 |
| **Revision** | 每段交付物完成后、进入下一步前 | 功能完整性、代码质量、设计一致性 | 通过 → 下一段 / 打回修改 |
| **Escalation** | 关键里程碑（Phase完成） | 全流程贯通性、跨模块一致性 | 通过 → 继续 / 暂停重评 |
| **Final** | 全量完成后、交付前 | 需求覆盖率、功能测试通过、设计审查 | 通过 → 交付 / 大改 |

### 审查清单通用模板（每段交付物必查）

1. **JS 语法正确性** — `node --check` 验证所有 script 块
2. **功能完整性** — 对照本阶段规范逐项验证
3. **设计一致性** — CSS 对照 design-tokens，无硬编码颜色/字号
4. **数据正确性** — API 响应字段完整、无字段名拼写错误
5. **Hermes 对照** — 与 Hermes 原生功能 1:1 对齐（如适用）

## 后续动作（必须全部执行）

1. 如果"新发现的原则"不为空 → 写入工作台原则Tab
2. 如果发现系统性问题 → 创建/更新相关skill
3. **执行全量备份** → 加载 `session-backup-discipline` skill 并执行五层备份
4. 归档到<vault>

## REFERENCE（参考体系）

- **Scrum Sprint Retrospective 模板**：Start/Stop/Continue 三栏复盘法，为本skill的"做得好/需改进/新原则"提供结构化对照
- **控制论五原理对照表**：反馈闭环→验证机制、分层递阶→多Agent约束、稳定性优先→增量叠加、信息质量→状态准确、适应与自组织→原则提炼
- **Google Post-mortem 文化**：无责复盘（Blameless），聚焦流程改进而非追责，是本skill"不追责只改流程"的制度根源

## LIMITS（边界与约束）

1. **复盘不追责只改流程** — 复盘目的是修正流程和原则，而非追究个人责任
2. **不超过30分钟** — 单次复盘控制在30分钟内，避免冗长无效讨论
3. **不要记录敏感人事信息** — 复盘文档中不记录涉及个人隐私或人事评价的内容
4. **发现的问题要立即补入原则** — 复盘中识别的改进项必须立即写入原则体系，否则复盘无效
