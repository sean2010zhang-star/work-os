## 一、Skill三级分层

### 分层标准

| 层级 | 特征 | 可靠性 | 判断需求 |
|------|------|--------|----------|
| 原子(Atoms) | 单一用途, 确定性 | 最高 | 无需 |
| 分子(Molecules) | 2-10原子组合 | 稳定 | 适度 |
| 化合物(Compounds) | 多分子编排 | 人类兜底 | 多层 |

**三条铁律:**
1. 调用方向单向: 化合物→分子→原子，不可逆
2. 可靠性递减: 原子 > 分子 > 化合物
3. 杠杆效应: 1化合物 = 10分子 = 100原子

### 置信度评分

- 每次成功使用 → +0.05 (上限0.95)
- 每次错误/修正 → -0.15
- <0.5 → "待修订"队列
- >0.85 + 3+项目使用 → "金skill"

## 二、外部审计 (按复杂度分级)

### 触发条件

| 复杂度 | 判定条件 | 审计手段 |
|--------|----------|----------|
| 无 | M1/M2, ≤3 calls | 不触发 |
| 低 | M3-M6, ≤10 calls | 客观工具 |
| 中 | M7-M10, 10-30 calls | 客观工具 + 独立LLM |
| 高 | M11+, 30+ calls | 客观工具 + 多模型交叉 |

### 客观工具审计 (所有级别)

```
[ ] py_compile / node --check — 语法检查
[ ] curl API端点 — 可用性
[ ] grep mock/setTimeout — 前后端打通
[ ] 文件完整性 — 预期文件存在且非空
```

### Agent Team审计 (中/高级别)

```python
delegate_task(tasks=[
    {"goal": "代码质量: 命名/错误处理/类型标注/重复",
     "toolsets": ["terminal", "file"]},
    {"goal": "架构评估: 接口/依赖/DRY/可测试性",
     "toolsets": ["terminal", "file"]},
    {"goal": "安全+边界: 输入验证/异常/注入/边界值",
     "toolsets": ["terminal", "file"]},
])
```

**关键约束:**
- 独立上下文(不看执行过程)
- 只读权限(不修改代码)
- 模型不可用 → 主Agent用execute_code补充

### 多模型交叉审计 (极高级别)

3个不同LLM独立评审，共识机制:
- ⭐ 三方共识 → 高置信度，必须修复
- ✓ 两方共识 → 中置信度，建议修复
- ? 单方发现 → 低置信度，人工判断

### 审计-修复循环

```
审计(发现P0) → 修复 → 重审(可能发现新P0) → 修复 → 重审(P0=0) → 放行
```

**评分提升规律(实测):**
- 安全分提升最快(5.3→8.5, +3.2): 有明确修复模式
- 代码分提升最慢(6.0→7.5, +1.5): 需要深层重构
- 每次修复可能引入新问题

## 三、交付后复盘

### 触发条件
- 完成Sprint/版本交付
- 修复重大bug后
- 用户明确不满时

### 控制论五原理自检

1. **反馈闭环** — 交付前是否执行了验证？
2. **分层递阶** — 是否先规划再执行？
3. **稳定性优先** — 是否增量叠加而非全量重写？
4. **信息质量** — 状态信息是否准确？有无"声称完成但未验证"？
5. **适应学习** — 是否从错误中提炼了新原则？

### 复盘输出

```markdown
# 复盘：[任务名]
## 做得好的: ...
## 需要改进的: ...
## 新发现的原则: → 写入skill或铁律
```

**复盘不追责只改流程。发现的问题立即补入原则。**

## 四、体系健康度月度检查 (V2.0新增)

### 6个指标

| 指标 | 健康 | 警告 | 危险 | 数据来源 |
|------|------|------|------|----------|
| 铁律违反频率 | <2次/月 | 2-5次 | >5次 | session_search |
| Sprint管理开销比 | <30% | 30-50% | >50% | Gate成本报告 |
| Agent Team ROI | >3x | 2-3x | <2x | 审计token/P0数 |
| 备份完整率 | >90% | 70-90% | <70% | 备份记录 |
| Memory使用率 | <60% | 60-80% | >80% | memory工具 |
| Skill衰减率 | <10% | 10-20% | >20% | Curator统计 |

### 执行方法

每月1日运行:
1. 扫描session_search统计铁律违反
2. 从Gate报告提取开销比和ROI
3. 检查备份记录完整性
4. 读取memory使用率
5. 统计skill使用频率和衰减
6. 输出健康度报告

### 处置规则

- 指标全健康 → 无需操作
- 有警告 → 记录到月度报告，下次改进
- 有危险 → 立即处理(压缩memory/清理skill/修改铁律)

## 五、每日Skill审计

按控制论五原理审核每个skill(0-2分):

| 原理 | 0分 | 1分 | 2分 |
|------|-----|-----|-----|
| 反馈闭环 | 无验证 | 基本验证 | 自动化+恢复 |
| 分层递阶 | 混乱 | 基本分层 | 严格分离 |
| 稳定性 | 无处理 | 主要异常 | 全覆盖 |
| 信息质量 | 不明确 | 基本明确 | schema+示例 |
| 适应性 | 硬编码 | 可配置 | 自更新+版本 |

总分≤5 → "需优化"
重复/重叠 → "需合并"
过时 → "需归档"
