# 三省六部制工作流

## 核心映射

| 古代机构 | 职能 | Hermes对应 | 实现方式 |
|---------|------|-----------|---------|
| 中书省 | 草拟方案、分解任务 | coordinator | SOUL.md + plan-confirm-execute skill |
| 门下省 | 审核、封驳、退回 | coordinator质量门控 | coordinator SOUL.md的3轮Gate |
| 尚书省 | 执行落实 | builder/writer/researcher | delegate_task分发 |
| 吏部 | 人事/角色分配 | coordinator路由 | agent-team-execution skill |
| 户部 | 预算/资源 | coordinator | token预算/模型选择 |
| 礼部 | 文档/规范 | writer | writer SOUL.md |
| 兵部 | 工程实施/代码 | builder | builder SOUL.md |
| 刑部 | 测试/审查/QA | builder+gstack-qa | test-driven-development skill |
| 工部 | 部署/运维 | builder | deployment-patterns skill |

## 工作流程

### 1. 中书省（草拟阶段）
coordinator接收用户需求后：
1. 分析需求，识别关键决策点
2. 拆解为子任务，分配到六部（角色）
3. 写出任务交接单，明确每个子任务的输入/输出/标准
4. 提交给门下省审核

### 2. 门下省（审核阶段）
coordinator自审（或用户审）：
1. **封驳条件**：
   - 任务拆解不合理 → 退回中书省重新拆解
   - 角色分配不当 → 调整路由
   - 遗漏关键需求 → 补充后重审
2. **通过条件**：
   - 每个子任务都有明确的完成标准
   - 角色分配合理（研究→researcher，写作→writer，代码→builder）
   - 无遗漏需求
3. 最多3轮封驳，第3轮由coordinator直接修正

### 3. 尚书省（执行阶段）
各角色按分工执行：
- researcher做调研，附Bull/Bear分析
- writer写文档，按规范格式
- builder写代码，TDD流程
- 每个角色完成后交回门下省

### 4. 门下省（交付审核）
coordinator做3轮质量门控：
- Gate 1: 完整性 — 所有需求点都有输出
- Gate 2: 质量 — 格式规范、无错误、可读性好
- Gate 3: 一致性 — 各输出之间无矛盾
- 全部通过 → 提交用户

## 权力制衡

| 制衡关系 | 实现 |
|---------|------|
| 中书不能自审 | coordinator的拆解必须过Gate才能分发 |
| 门下可封驳 | coordinator有权退回任何不合格输出 |
| 六部各司其职 | researcher不写代码，builder不做研究 |
| 用户是最终裁决者 | 所有关键决策点提交用户确认 |

## 实际使用

用户说"用三省六部做XXX"时：
1. 切换到coordinator Profile
2. 按中书→门下→尚书→门下流程执行
3. 每个阶段完成后写review-log到 ~/wiki/projects/{项目名}/

用户不说时，日常任务仍用标准四角色流程。三省六部用于复杂项目的结构化管控。

## 与L1-L4执行框架的关系

三省六部是 **L4 大型工程** 的执行模式。详见 plan-confirm-execute skill 的L1-L4框架：

| 级别 | 模式 | 本skill参与 |
|------|------|-------------|
| L1 简单 | 直接执行 | 不涉及 |
| L2 并行 | delegate_task | 不涉及 |
| L3 复杂 | plan-confirm-execute | coordinator自审 |
| **L4 大型** | **三省六部** | **完整流程** |

**L4判定条件**: ≥5个模块、需架构设计、用户说"重新设计"/"从头构建"。

## PITFALLS (实测踩坑)

1. **三省六部制必须落地到代码差异** — 实测发现: 如果只是给middleware起名叫"门下省"但代码和其他系统一模一样，方法论就是空壳。正确做法: B2B系统的middleware要包含合规检查/审计追踪等B2B特有逻辑，不能用通用错误处理。
   - 错误: ComplianceBot的middleware和BidFlow一模一样
   - 正确: ComplianceBot的middleware应包含合规规则检查，BidFlow应包含标书格式校验

2. **GStack+Agent Team组合优于纯三省六部** — 独立审计评分: GStack 8.6 vs 三省六部 7.2。Pipeline思维(validator→processor→scorer→optimizer)产出质量最高。

3. **子agent滥用代替三省分解** — 症状：所有任务都用 delegate_task 单发子 agent，而不是按结构化流程执行；用户会质疑「为什么总是用子agent处理工作，不是有多agent协作的模式吗」。修复：
     - 中书省(我)负责规划和拆解任务，不是把整个任务丢给子agent
     - 尚书省用delegate_task(tasks=[...])并行执行，但每个task是明确的子任务
     - 门下省必须是独立Agent审核，不是我自己审自己
     - 审查院必须是独立Agent测试，不能是开发Agent自测
   - **正确模式**：
     ```
     中书省(我): 写方案+拆子任务 → 门下省(独立Agent): 审核方案
     → 尚书省(tasks=[A,B,C]): 并行执行 → 审查院(独立Agent): 测试+审计
     ```

2. **熔断器阈值变量混用**: circuit_breaker.py 有两个阈值 `HALF_OPEN_THRESHOLD=5` 和 `OPEN_THRESHOLD=10`，记录failure时必须先检查 `>= OPEN_THRESHOLD`(10次直跳open)再检查 `>= HALF_OPEN_THRESHOLD`(5次跳half_open)。如果把两个if的顺序写反或用错变量名，5次失败不会触发任何状态转换。验证方法：`for i in $(seq 1 5); do python3 circuit_breaker.py failure; done && python3 circuit_breaker.py status` 应输出"半开"。
3. **delegate_task写wiki文件需确认路径**: 子agent的工作目录可能不是预期目录，write_file时用绝对路径而非相对路径。
4. **新建基础设施的验证策略**: 用户偏好"先建设后验证，3个月不用自动删除"。新建脚本/规则文件后：(a)基础功能测试通过即可交付 (b)加staleness_check监控 (c)不追求上线即完美。
5. **审查院必须实测执行，不能只看报告数字** — 3 个并行审查 Agent，其中可靠性审查（刑部）必须**亲自跑** `node --test`、`cross-check.js --n 200` 等命令，拿到实测结果（205/205、800/800、真值抽查 3/3），才能判定"无断言造假"。如果只看项目 README 自称的数字，无法区分"真有"与"声称有"。实测核验是审查院区别于门下省（只看文档）的关键动作。
6. **审计 Agent 运行期间继续提交会造成基线漂移** — 审计 prompt 里的 HEAD/tag 判定项会在审计中途过期，产出假 P2「HEAD 不符」。开发者在等审计结果期间推进后续开发时：每次增量 commit 后用 `delegate_task(action='steer', subagent_id, message)` 通报新 HEAD、增量内容、判定基准修正，并为新范围追加专属必验项（steer 不中断子代理，实测有效）；审计范围宜写成「前门 tag..当前 HEAD」区间而非单点 commit；派审计前先把当期增量 commit——区间基线必须已落盘，未提交改动离子代理一条 git 命令的距离就是毁灭。若子代理已接近完成、steer 可能漏达，接受其按旧基线出报告，新范围另派复审。
7. **门下省封驳后的修订姿势：分型再分层** — 独立评审 REVISE 决策材料时，先给封驳论点分型：全称否定断言（「没有任何真值源」）最易被检索在局部层面证伪，而合规/政策类理由不受外部先例削弱。修订不是整体采纳或驳回，而是按可核性**分层**处置（可核层上线、未校勘层显式缺口不排、底本互斥层永不实现），修订稿保留 v1 错误逐条+证据 URL 清单作终审入口。
8. **评审意见本身也是待验证断言，逐条复验后才处置** — 独立评审 agent 会出错，全盘照单处置=把错判固化进计划。三类必复验：①数字类判定（checks/计数）自己在 HEAD 实跑一遍再改文档，评审报的数也可能带自己的测量误差；②「遗漏未排期」类判定先 grep git log/实装证据——已实装但上游文档未划线的项属文档债非排期债，错收会让计划里出现重复建设条目，处置时在修订稿写明「经 commit 核对驳回此条」；③评审引用自身上位文档的行号/事实，与被评对象一并核对防连环失真。驳回也要留证据（commit 哈希级）进修订稿，供下轮终审倒查。
10. **口诀/查表类知识必须核对底本原文入库，「代码+测试+注释三面一致」不构成正确性证明** — 凭记忆默写的领域表（口诀、公式、换算表）会把同一份幻觉同时写进实现、测试断言、basis 注释，三面互相印证地错；自署「出处：某古籍」的字符串也不是证据。正确工序：入库前 web 检索底本原文并至少两源交叉（识典古籍/权威站点级），入库后派审 prompt 要求评审员对表逐字核原文——实测一次复审靠底本揪出了开发+测试+首轮材料审都漏掉的误标出处条目。修订时同步改三处（表、锚点测试、计划文档计数口径），并在 commit message 留「凭记忆默错→底本纠出」实录供纪律追溯。订正后必须 grep 全仓旧口径关键词（表头注释、区块行内注释、JSDoc、docs 计数），同 commit 一并清——处置版若只改数据面不改注释面，残留的旧口径注释会被下一轮复审作为唯一 blocking 驳回（同类错误以注释形态再活一轮）。
11. **篡改红测的守护力=篡改后断言盘面必红，按「表值强断言」设计测试盘** — 红测只证「断言依赖被篡改值」才有效：若断言样本的输入集不含被篡改的目标值（例：查表行 丑→申 被篡，但样本盘根本不含申/丑任一），全套测试照样绿=防线名存实亡。查表型函数每个表行至少配一个使结果命中的正例盘，且把行值字面钉进断言（`targets[0]==='丑'` 或 basis 串含「寡宿在丑」）；派审查院时把「逐行篡改必红」写成红测规格而不是抽查。锁强度三查（复审验收弱锁时逐条问）：①**分支覆盖**——回归锁里 if/else 两分支各需一个 fixture 使其执行，写在「永不成立的 if」内的断言=零锁（例：测试盘恰好命身同宫，异宫上屏分支永不跑，行为对但锁未覆盖，另盘实测才发现）；②**类型锁升级内容锁**——`typeof x === 'string'` 对键名笔误的回退产物 `''` 同样通过（逃逸），提取类字段断言必须=值落合法名单集合+环排结构（如 12 宫值互异），不接受「在场即可」；③**时间窗半锁配对**——依赖运行时刻的等值断言（本地日期 vs UTC 日期只在 0-8 时分歧）只在部分时段红，必须配对一个旧坏值全天必红的断言（格式/类型/非空 match，null 传进 assert.match 即抛）。
9. **双审并行分工要写死「材料面 vs 实测面」防重叠互等** — 门下省（只读审文档 vs diff 一致性、红线逐句扫描）与审查院（禁改仓库、亲跑测试+篡改红测+独立请求复核）同一批 dispatch 并行发出，prompt 里各自声明对方不做的部分；审查院红测模式=临时改动先 cp 备份**到工作树外**、测完用 cp 原文件覆盖恢复——**严禁子代理用 git checkout/stash/reset/clean 恢复主树**（恢复到 HEAD 会静默冲掉主会话并行开发中其他期的未提交改动：实测评审员篡改恢复一次清空了新模块接入的全部接线，字段凭空消失、测试变红是唯一暴露点，纯靠运气发现）；子代理要干净基线就 `git worktree add /tmp/xxx <sha>` 或 cp 副本内篡改，派单 prompt 第一段硬约束「禁止主树一切 git 写命令与仓库文件修改」；「篡改后对应断言必红」比「测试全绿」更能证明闸真实存在。**父会话侧的配套纪律是「冻结」**：即便子代理被禁 git 写命令，篡改红测仍必然临改仓库文件再恢复（恢复动作有走 git restore 的残余风险）——所以派审的正确时序=当期 commit+tag 完成后冻结主仓库编辑直到交卷，派单 prompt 里写明「主会话已冻结，HEAD 不会变，放心按区间读」；审期间继续开发新期=新未提交改动重新进入毁灭半径，两害相权，串行冻结换并行开发连续性的做法只在当期改动已全量落盘时才可接受。子代理被冲树/基线漂出区间时立即 stop（partial 结果照收），按新基线区间制重派，不要让它在失效地面上跑完出报告。
12. **篡改/新增测试先红时，先审断言侧** — 新写测试的期望值错概率高于被测实现对：实测连续四类断言自错（命中柱位置凭记忆写反、星名单漏列新项、单字表值「衰」被 `length>=2` 误杀、库实出 10 位被想象成 12 位）。处置序：先独立重算期望值（引擎实跑 dump 形状 / 手工按序号数 / 打印实际返回再定断言），确认断言侧为真才改实现——第三方库结构断言同样守此律。探针 vendor min.js：UMD 库在裸 node 下需先 `globalThis.self = globalThis` 再 require；探针脚本每个提取点 try/catch 后只输出聚焦 JSON（压缩库内嵌 throw 源码字符串，裸跑异常会把整份 minified 体刷进终端输出淹没有效信息）。
13. **浏览器 E2E 的 localStorage 门与凭证会被前轮清理波及** — 多轮测试会话里手动 removeItem 清 consent/凭证后，后续所有页面的 E2E 都回落年龄门/档位拦门（免费用户态）产生「功能没上屏」假信号。固定开局序：先 goto 任意同源页 → setItem 年龄签名+注入档位凭证（tier 按被测功能要求签，高级盘要 pro）→ 再导航被测页；看到 claims=0 先查 gate/档位拦（result 区文本含「该盘属于 X 档」即凭证拦），不要先怀疑新代码。
14. **commit/文档里的申报数字必须粘贴自实跑 stdout，禁止心算增量** — 「369+新增2=377」这类推算必错（改造既有条目不加计数、删条目减计数、并行期他人合入都会漂移）；发现即 amend 重打 tag 订正 message（未派审前 amend 安全，审中禁用——区间 hash 会被复审抓到漂移）。同理：测试注释里的「库实出 N 位」也要探针实测，不写想象值。口诀/名单类常量默写第三次仍错（岁前十二神纸面底本版与库内环排版不一致）——一律多盘探针提取全集后入库并在测试注释声明「名单=库实际环排，非纸面底本」。
