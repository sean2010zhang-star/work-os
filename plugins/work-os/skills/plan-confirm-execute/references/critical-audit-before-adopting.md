# 学习外部方法论前的批判性审计流程

## 何时触发
- 用户说"学习这个""看看有什么借鉴""深度分析提升点"
- 拿到外部文档/教程/论文，要决定是否引入现有系统
- 竞品分析、技术选型、方法论评估

## 核心原则
**不是"文档说了什么"，而是"我的系统实际需要什么"。**
外部方法论解决的是通用问题，你的系统有特定状态。两者必须交叉验证。

## 四步审计法

### Step 1: 读文档，提取核心观点
列出文档的3-7个关键主张/方法/模式。

### Step 2: 查系统实际状态（实证，非假设）
对每个观点，用工具验证系统当前真实状态：
- 跑命令确认（不是靠memory里的描述）
- 查数据库/文件的实际数据
- 检查功能是否真的在工作（不是"已部署"就等于"在运行"）

常见陷阱：
- Memory说"已部署60实体" → 实际sync脚本crash，实体是死数据
- 说"473个skills" → 185个是第三方导入，从未使用
- 说"97%爆满" → 实际是2142/2200字符，功能上正常

### Step 3: 逐项判断"真正缺口"vs"已有能力"
对每个观点做三列判断：
| 文档观点 | 本体系现状 | 真正缺口 |
|----------|-----------|---------|
| X能力 | 已有Y | 缺Z，因为... |

关键判断标准：
- 如果现状已覆盖80%+ → 不需要引入
- 如果缺口存在但使用频率低 → 等触发条件再引入
- 如果功能"看起来在工作实际已坏" → 修bug优先于增功能

### Step 4: 定义触发条件（不是预防性引入）
对每个有价值但当前不需要的观点，定义：
- **触发条件**: 什么具体事件/指标出现时才引入
- **具体指标**: 可量化的阈值（如"月调用>200次"）
- **引入方式**: 轻量版→完整版的渐进路径

## 输出格式
```
P0 [时间] 修复项 — 已坏但看起来在工作的
P1 [时间] 高优改进 — 有真实缺口且高频使用
P2 [时间] 中优改进 — 有缺口但低频使用
其他: 列出触发条件，等痛点出现再引入
```

## 反面模式
- ❌ 文档说X好 → 直接引入X（未验证是否需要）
- ❌ "预防性过度工程" — 还没遇到问题就先建防御体系
- ❌ 把文档的使用场景等同于自己的使用场景
- ❌ 只看功能匹配，不看使用频率/规模匹配
