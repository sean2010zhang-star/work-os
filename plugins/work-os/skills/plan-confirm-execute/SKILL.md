# 方案确认三步走 Skill

## 触发条件
- 用户提出的功能需求涉及2个以上文件修改
- 新功能开发（非简单bug修复）
- 架构调整或重构
- 前端页面开发/重写
- 多Agent并行任务

## 执行模式选择 (L1-L4)

**必须在开始工作前判断任务复杂度，选择对应执行级别：**

| 级别 | 适用场景 | 执行方式 | 示例 |
|------|----------|----------|------|
| **L1 简单** | 单文件/小修改/查询 | 直接执行，不加载额外skill | "改个配置"、"查个状态" |
| **L2 并行** | 多个独立子任务 | `子代理` 并行分发 | "同时写3个文档"、"并行检查多个服务" |
| **L3 复杂** | 多步骤需确认 | 本skill：plan→confirm→execute | "重构某模块"、"新增功能" |
| **L4 大型** | 多引擎/多模块/系统级 | 三省六部制多agent+分阶段+checkpoint | "7引擎多模块系统"、"全栈应用重构" |

**判定规则：**
- 涉及 ≥3 个独立模块/文件 → L3+
- 涉及 ≥5 个模块 或 需要架构设计 → L4
- 用户要求"重新设计"/"从头构建" → L4
- 不确定时，**上浮一级**，宁可过度规划也不要遗漏

**铁律：L3/L4 任务必须先加载相关skill再执行，跳过不可跳过。**

## 流程

**在做任何分析或方案之前**，先扫描可用skill列表，加载与当前任务相关的skill。

```
[ ] 用 skills_list 扫描可用skill
[ ] 用 加载skill 加载匹配的skill（即使觉得"我会做这个任务"也要加载）
[ ] 如果涉及前端 → 加载 frontend-* / design-* 相关skill
[ ] 如果涉及商业化 → 加载 opc-* / startup-* 相关skill
[ ] 如果涉及评估报告 → 加载 buzheng-* / pinggu-* 相关skill
[ ] 如果涉及Git/版本 → 加载 project-git-version
[ ] 如果无匹配skill → 继续，但说明"无相关skill覆盖"
```

常见反例: 多引擎系统重新设计时，直接开始写代码和文档，没有加载plan-confirm-execute本身，也没有扫描相关skill。用户明确指出"Agent的工作模式是否按原则执行"。根源：跳过了skill扫描步骤，导致工作流选择缺失。

**铁律**: 复杂任务不加载skill容易遗漏关键流程。宁可多加载一个不需要的skill，也不能遗漏关键skill。

## 流程

### Step 1 — Comprehensive Gap Analysis（必须先做）
输出方案之前，先用「实证数据对比」取代「主观猜测」。针对每个功能域：

1. **查现有数据模型**：读真实 schema/文件/API，而非假设
   - 数据库：`sqlite3 <db> ".schema"` 查完整建表语句
   - JSON文件：`python3 -c "import json; ..."` 枚举所有 key
   - API响应：`curl` 实际调用，看完整字段

2. **列「有/缺」矩阵**：每行一个维度，填 本体系有/目标项目缺/影响程度

3. **识别致命缺口**：有2个以上「致命」缺口时，必须优先处理
   - 致命 = 系统级风险（数据丢失/安全/多Agent冲突），不只是体验不佳

4. **分类改进项**：按优先级+复杂度分组，给用户选择权

**常见反例**：方案只列少数改进点，用户追问"只有这些？"——根源是没做完整 schema 对比就出了方案，属于「分析不足就交付」。

**Gap Analysis Checklist（每项必查）**：
```
[ ] 数据库/文件 schema 完整读取（不能只读头几行）
[ ] 所有唯一字段枚举（找隐藏字段如 reasoning/context/complexity）
[ ] 枚举所有 status 值（running/pending/pending_approval/error 都算）
[ ] 致命缺口识别（claim_lock防重分发、assigned_agent明确责任人）
[ ] 改进项按 P0致命/P1高/P2中/P3低 分类
[ ] 告知用户：「第一期先做P0/P1，下次迭代做P2/P3」
```

---

### Step 2 — 写方案
输出以下内容到 `PLAN.md` 文件：

```markdown
# 任务：[任务名]
## 目标
[清晰的一句话目标]

## 现状分析（来自实证数据）
- 当前代码结构
- **完整**字段/表 schema（不要只列自己记得住的）
- 需要修改的文件
- 可能的风险点

## 方案设计
### 修改范围
| 文件 | 操作 | 说明 |
|------|------|------|

### 实现步骤（编号）
1. ...
2. ...

### 设计规范
- 引用 DESIGN.md 或说明使用的CSS变量/组件

### 风险评估
- 可能影响的功能
- 回退方案

## 验证标准
- [ ] 具体验证项1
- [ ] 具体验证项2
```

### Step 2: 等用户确认
- 将PLAN.md展示给用户
- **明确提问**："请确认此方案是否可以执行？有需要调整的地方吗？"
- 等待用户回复确认
- **禁止**：未确认就开始编码 — 容易偏离需求，返工成本高

### Step 3: 执行
- 按PLAN.md中编号的步骤逐步执行
- 每步完成后更新PLAN.md中的完成状态
- 全部完成后运行 diagnose.py 验证

## 高危场景（极易跳过确认的时机）
- **分析后冲动实施**：做完竞品分析/对比分析后，兴奋地直接开始"借鉴改进"，跳过方案确认。
- **学习后立即应用**：学完新技术/新方法论后，迫不及待地改代码，没有先规划改哪里、怎么改。
- **用户说"提升/改进/优化"**：这类模糊指令容易让agent自行解读范围，必须先确认scope再动手。
- **参考设计对齐不足**：用户给出参考页面(如HoloDash)，直接开始编码而没有先截图分析参考设计的每个视觉元素，导致"差距很大"。 — 正确做法: 先用vision_analyze分析参考图的每个CSS属性，列出现状vs目标的差距矩阵，再逐项实现。
- **headless浏览器与用户浏览器差异**：Browserbase headless渲染可能与用户实际浏览器不同。用户看到的问题可能在headless中看不到。遇到"效果不对"时，优先问用户具体哪里不对，不要自认为效果已经到位。

## 反骨架铁律 （全栈项目实战教训）

用户明确纠正: "我需要的是所有设计功能均已完成，而不是每次都只给我完成一个骨架。"

**骨架 = 交付失败** — 以下任何一项都说明功能未完成:
- 前端页面用 `setTimeout` / `MOCK_` 常量 / 硬编码假数据
- 后端端点存在但前端组件从未调用 `api.ts` 中的对应方法
- 模块有 router 文件但返回 stub (`{"message": "V2.0上线"}`)
- AI 功能未接真实 LLM API（至少要有 fallback 路径）
- 数据库模型存在但无实际 CRUD 操作

**验收标准(Gate 2必须验证):**
```
[ ] 后端: 每个API端点有真实DB操作(grep 'await db.execute' / 'db.add')
[ ] 前端: 每个页面调用api.ts中的方法(grep -n 'API\.' / 'api.')
[ ] 前端: 无setTimeout模拟异步(grep -rn 'setTimeout' --include='*.tsx')
[ ] 前端: 无MOCK_/mock常量(grep -rn 'MOCK_' --include='*.tsx')
[ ] 集成: curl端到端测试通过
```

## 反面模式（禁止）
- ❌ 边想边做，没有先出方案 — 缺乏规划容易遗漏关键点
- ❌ 自己认为方案没问题就直接开始 — 用户视角可能不同
- ❌ 方案只写给自己看，不展示给用户 — 失去确认环节
- ❌ 做完分析后直接进入实施（最常见违反）— 分析结论可能有偏差
- ❌ 参考设计对齐不足 — 用户给出参考页面(如HoloDash)，直接开始编码而没有先截图分析参考设计的每个视觉元素，导致"差距很大"。 — 正确做法: 先用vision_analyze分析参考图的每个CSS属性，列出现状vs目标的差距矩阵，再逐项实现。
- ❌ headless浏览器与用户浏览器差异 — Browserbase headless渲染可能与用户实际浏览器不同。用户看到的问题可能在headless中看不到。遇到"效果不对"时，优先问用户具体哪里不对，不要自认为效果已经到位。
- ❌ **声称"完成"但实际是骨架/Stub** — Gate全部PASS但需求审查完成度不足一半。前端用mock数据，后端有API但前端没调用。**必须做需求-功能对比审查+前后端打通验证后才能声称完成。**
- ❌ **跳过模式选择直接执行** — 任务到达必须先判定工作模式(work-mode-selector)，不可跳过
- ❌ **不加载相关skill就动手** — M7+模式必须先加载对应skill再执行
- ❌ **学完新方法论直接套用** — 外部文档/教程的观点建议先与实际系统状态交叉验证，再决定是否引入。详见 `references/critical-audit-before-adopting.md`
- ❌ **用户确认后仍输出方案摘要** — 用户说"继续"/"按方案进行"后，直接开始tool call执行，不要再输出"方案已确认，开始执行Sprint 1"之类的文字。用户需要看到的是实际产出(文件创建/代码修改)，不是执行计划的复述。- ❌ **交付骨架/Stub冒充完成** — 文件存在≠功能完成。前后端必须真实打通（API调用成功+数据正确返回）。用户反馈原文："交付是失败的，没有达到要求"。（全栈项目实战教训）
- ❌ **声称"全量开发"但只完成一小半** — 必须对照设计文档逐功能验证完成度，不能自我感觉良好。审计Agent必须独立对比设计vs实现。

## 与其他流程的关系
- 如果任务复杂到需要多Agent并行 → 先走本skill，确认后走三省六部
- 如果涉及前端 → 方案中必须包含DESIGN.md引用
- 如果涉及商业化 → 方案中必须引用OPC方法论

## REFERENCE（参考体系）

- **Amazon 6-pager / PRFAQ 模板**：结构化叙事替代PPT，为本skill的方案文档格式提供范本——先写清楚再动手
- **工程控制论反馈闭环**：方案→确认→执行→验证构成完整闭环，确认是关键反馈节点，跳过则闭环断裂
- **PRFAQ（Press Release + FAQ）**：先写发布稿再倒推实施，与本skill"先出方案再执行"的逻辑一致

## 连续执行授权

当用户说"开始执行"、"开搞"、"go"、"继续"、"按这个进行"等确认语时：
- 授权当前方案的**所有Sprint**连续执行
- 每个Sprint仍需Gate验证，但不需要每步等用户确认
- Gate PASS → 自动进下一个Sprint
- Gate FAIL → 修复重试，3次FAIL才Escalation
- 这与"sprint-gated-delivery" skill配合使用
- **"继续"≠"重新规划"**: 用户说"继续"时，期望看到立即的代码/文件产出，不要输出新的方案摘要或重复已确认的内容。直接调用写文件/执行代码/跑命令开始执行。

## 跳过确认授权（全栈项目实战教训）

用户说"不用等我确认"、"自行执行"时：
- 跳过方案确认步骤，直接执行
- 使用Agent Team做独立审核代替用户确认
- 审核通过后自动推进下一阶段
- 审核不通过则修复后重新审核

用户原话："该项目由Agent自行执行，不用等我确认，选择team agent进行审核就行"

## 大版本升级专用流程

对X.0级别升级(如v3→v4)，Gap Analysis需额外步骤：
1. **读完所有现有文档** — 路线图/架构设计/数据库设计/审查报告/统计报告，不遗漏
2. **对照路线图定义的下一阶段目标** — 路线图通常已定义核心功能，不要自行发明
3. **统计当前代码基线** — 文件数/代码行/API端点/模型数，作为增量衡量基准
4. **识别致命缺口** — 路线图要求但现有代码完全没有的能力(如多租户→无tenant模型)
5. **按Sprint分组** — 每个Sprint一个独立可交付的能力增量，含新增+修改文件清单
6. **技术方案要点** — 关键决策(如隔离策略/支付集成方式)需明确写出

## LIMITS（边界与约束）

1. **方案确认前禁止动手写代码** — 未经用户确认的方案进入编码阶段容易偏离需求
2. **简单bug修复不触发此流程** — 单文件、单点修复无需走方案确认，直接修复
3. **确认等待不超过1轮** — 方案确认只等1轮问答，超时未回复视为默认同意
4. **用户沉默超24h视为同意（或再次询问）** — 超过24小时未回复，可视为默认通过，或再问一次后执行
