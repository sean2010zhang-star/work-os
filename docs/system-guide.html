本文档回答一个问题：装上 Work OS 之后，你的 Agent 到底会怎样工作？ Execution discipline for AI agents — 每个任务先路由、按复杂度分档、被 Gate 闸门强制验证、 每次教训回灌记忆。规则不是文档建议，而是安装即用、自我进化的系统层。

01 · 为什么需要它 Why this exists

Agent 的失败模式是普适且昂贵的。纯文档纪律在压力下总被无视——所以我们把它做成可安装的软件。

六种典型失败 · six failure modes
  • mock 数据冒充"已完成" — 前端跑通是因为没接真后端
  • 审计子代理冲掉未提交工作 — checkout/reset 无声回滚
  • 测试夹具掩盖回归 — 手造字段与真实输出形状不符
  • 汇报数字与数据源漂移 — 页面写死常数，复现即穿帮
  • "全部通过"经不起独立复查 — 自评自证，无独立上下文
  • 12 小时自主跑凌晨崩掉 — 无检查点、无回滚、无预算熔断
核心信条 · core belief

无验证的交付 = 开环系统 = 不可控。

Unverified delivery is an open-loop system. Work OS 用四个机制把开环变闭环：

① 路由先行 ROUTE-FIRST ② 铁律 IRON LAWS ③ Sprint×Gate 闸门 ④ 记忆回灌 MEMORY LOOP

纪律要么可强制，要么是装饰。Docs advise; gates block.

03 · 单任务处理主流程 Core loop — one task, end to end

任何非闲聊任务都走这条链。注意左侧记忆轨道：任务前"读"、任务后"写回"，构成闭环——这是系统越用越锋利的机制根源。

铁律在流程中的位置：L1 路由先行 → 铁律①方案确认（L3+）→ 铁律②真实打通（G3）→ 铁律③备份不可跳（收尾）→ 铁律④Gate 不可跳（3 FAIL 上报）→ 铁律⑤完成度 <80% 不许说"完成"（交付前逐项标 ✅⚠️❌）。

04 · 复杂度分档与 Sprint×Gate Tiers & gates

路由决策块的第二行输出复杂度，直接决定后面走哪条路、开几道闸。

复杂度 L1–L4

级别判据方案确认执行方式
L1≤2 文件 / 查询免直接做
L2独立子任务免并行子代理
L3多步骤 / 4–10 文件需要（PLAN→确认）主 Agent + skill 链
L4多模块 / 架构 / 10+ 文件需要分角色制衡 / 分阶段

Sprint 级别 → Gate 要求

级别判据Gate交付件套
轻量≤3 文件 (L1-L2)G1+G2commit+tag + 一行摘要
标准4–10 文件 (L3)G1–G4完整 4 件套
重型10+ / 架构 (L4)G1–G54 件套 + 全量备份 + 交叉审计

G5 用户价值门：对照合同/设计文档逐项验证"用户真的得到了什么"，通过后才允许声明完成。

05 · 规则三层 Laws · recommendations · red-lines

三级语气即三级优先级：铁律违反 = 交付失败；建议跳过必须写明理由；红线全部来自实测事故。

5 条铁律 · 违反 = 交付失败
  1. 方案确认后才能执行（L3+ 先写 PLAN；"go/继续"= 授权连续执行）
  2. 前后端必须真实打通（mock / setTimeout 假响应 / 未接真实 LLM 都不算完成）
  3. 备份不可跳过（每 Sprint 至少 commit；"下次再备份"= 现在就做）
  4. Gate 验证不可跳过（轻量至少 G1+2；3 次 FAIL → 上报，不静默跳过）
  5. 完成度 <80% 不许说"完成"（对照设计文档逐项标 ✅⚠️❌📅）
10 条强烈建议 · 违反需写明理由
  • 任务到达先判定模式（M1–M18）并告知用户
  • L3+ 必须加载对应 skill，按其流程执行
  • Phase-by-phase 自审查：每阶段自检后 commit
  • 批量文件操作用主 Agent 代码执行工具，不派子代理
  • 核心算法 / 架构决策不委托子代理
  • 审计代理只读；并行期禁 checkout/stash/reset；范围区间制
  • P0 修复后必须重审，迭代到 P0=0
  • 先验证再改：选型/架构变更先做 spike 实验
  • 用户反馈是最终校准器：指标 PASS 但用户不满意 = 重审
  • 规则用硬语气（铁律/必须/禁止），文档同理
质量红线 · 实测事故精华（节选）
  • 测试夹具必须用引擎真实输出形状（先实跑 dump），手造字段 = 掩盖退化
  • 页面/文档数字一律动态取自与复现命令同一数据源，禁手写常数
  • catch 必须区分 fetch 失败与代码异常；吞 TypeError = 把缺陷伪装成"离线"
  • 分享/导出通道对文本内容做敏感遮花；只扫键名防不住用户写进内容
  • 仓库内静态服务默认仅绑 127.0.0.1 + 敏感路径硬 denylist——代码合规 ≠ 部署合规
  • 价格/档位/效期唯一真相源 = manifest 数据文件，UI 字面量必漂移
  • 前端保持参考代码原风格——品牌 ≠ 风格
  • 版本更新默认不同步云端，用户明说 deploy 才部署

06 · 长程自主战役协议 V3.4 Campaign edition — long unattended runs

场景：用户说"全量开发、不用等我确认、测试审计通过后自动进下一阶段，直到全部完成"。战役协议把这句话变成有边界、可恢复、可审计的闭环，而不是无限自主承诺。关键调和：确认前置——Mission Contract 签署就是那次"方案确认"。V3.4 的标志变化：能静态判定的规矩一律下沉为机检脚本，文字叮嘱升级为 fail-closed 闸门。

该协议的迭代靠对抗评测驱动（见 profile/skills/protocol-doc-benchmarking/）：真实事故改编的迷宫题 + 预先写死的中立判据 + 每轮全新 Runner 复跑——对称题曾给融合版 97.5/100，同一文档换真实事故题仅 66，这个偏置教训本身就是方法论的第一条。

07 · 记忆闭环 The memory feedback loop

纪律管第一次做对，记忆管第二次更聪明。分层原则：长期结构化 → 记忆库文件；碎片事实 → 宿主 memory 工具；过程证据 → 会话历史检索。

文件内容更新时机

偏好.md用户工作偏好、审美约定、环境速查用户表达新偏好 / 纠正时（首次运行强制采访填写）
工作流规范.md沉淀出的标准流程 + 事故教训出现新标准流程 / 教训时

自进化通道（Hermes Edition）：Agent 在工作中沉淀的新流程直接写入 profile skills——技能库随使用生长，Universal Edition 为手动编辑。

2 分钟首跑验收 · acceptance test

装好后对 Agent 说："给我的 Flask 应用加认证，并做一个 React 登录页"——
正确安装的 Work OS Agent 会在写任何文件之前先输出 [路由] 决策块（分类=代码 | 复杂度=L3 → 需要 PLAN 确认），并给出可证伪的"联调完成"判据。再跑一个小真实任务，检查收尾：commit+tag 做了？完成度逐项 ✅⚠️❌ 了？两头都对，L1 纪律层即已生效。
